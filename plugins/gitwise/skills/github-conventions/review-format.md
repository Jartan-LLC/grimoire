# Code Review Format

Recommended structure for code-review comments posted to GitHub pull requests.

## Template

```markdown
## Code Review

**Files reviewed:** [count] files across [categories]

### Critical Issues
<!-- 'None found' if empty. Number findings 1., 2., 3. -- never #1/#2 (auto-links to issues/PRs). -->
1. **[Title]** -- `path/file:line`. What's wrong, and the fix.

### Important Issues
[list, or 'None found']

### Minor Issues
[list, or 'None found']

### Summary
<!-- Do NOT write #1/#2/#3 or "issue #N" here -- GitHub renders #N as a link to that
     issue/PR. This section is where a stray #N slips in most often. Refer to findings
     as "Finding 1", "the first Critical item", or a plain "1." instead. -->
[overall assessment]

---
*Generated by Claude*
```

## Guidelines

- **Severity buckets** -- group findings under Critical (must fix) > Important (should
  fix) > Minor (consider fixing). Empty bucket -> `None found`. These match the reviewer
  agents' severity tags.
- **Numbering** -- number findings `1.`, `2.`, `3.`; refer to one as `Finding 1`. Never
  use a bare `#1`/`#2`/`#N` -- GitHub turns it into a link to that issue/PR. This is the
  one convention most easily broken in the free-text **Summary**. See the numbering rule
  at the top of [SKILL.md](SKILL.md).
- **Be specific** -- every finding carries a `path/file:line` and a concrete fix, not just
  a complaint.
- **Line-specific findings** -- prefer an inline PR review comment on the exact line over a
  bullet in the summary comment.
