# Docs Pages (`docs/` and docs sites)

Any page under `docs/` or on a docs site that has no file of its own in docs-patterns (a changelog page follows `changelog.md`): how-to, reference, explanation and tutorial pages, runbooks, operator guides, architecture pages and the home page. The project's own rules win where they speak. Unless your task is the page itself, apply these lines only to what your change adds or makes false.

- Write for the release a reader's install steps give them, unless the docs are built per version, say they describe the default branch, or the project has no release. Mark newer behaviour with its version ("from 0.3.0") where the tree or the release record gives it, else as unreleased, and name versions by number ("servers before 0.2.0"), never "an earlier version" or "a version carrying this fix".
- Mark planned or target state where you state it, in the sentence or the section heading, with its issue; on a task page (how-to, runbook, operator guide) or a reference page, leave plans out, as plain-writing says. A note at the top of the page does not mark the lines below it.
- Give the page one reader and say its scope in its first lines: what it covers and which page has the rest. Where two readers need different parts, split the page or give each a section headed for them. Write the scope, not a label for the page's type.
- Title a how-to by its task. Order its steps as the reader does them, with each check before the step it decides, and put every action the task needs in the steps or link it from the step where it applies.
- A generated reference covers the surface the project supports; leave the rest out or label it internal.
- In a runbook, start each scenario with containment where it has one, then the fix, and end it with how to tell it is over and the step that undoes the containment, or why none is needed.
- Name only files, settings and commands that exist, unless the line or its section heading marks them planned, or the line marks them removed or renamed (with the version, where the first line asks for one), or they are placeholders an adopter replaces. Where another page states the same setting, default or step, keep it in one place and point to it from the others.
