# Security Policies (SECURITY.md)

The project's own rules win where they speak. Ask the user before writing a channel, a promise or a supported-versions rule the project has not settled; what the inputs state, or the task asks you to define, is settled. In the PR description, name what the user settled when you asked. If nobody can answer, leave out only the unsettled part and say so there. Edit the file GitHub shows: `.github/SECURITY.md`, else the root, else `docs/`, else the owner's public `.github` repository, whose file covers every repository without its own; for one repository that has only the owner's file, write its own file unless the task is the owner's policy. Put a new file where the docs already link it, else the root. Unless your task is the policy itself, apply these lines only to what your change adds or makes false, keep the lines it does not touch, and name in the PR description a public route or a dead channel you leave.

- Name a private channel that works for everyone the file covers. If it is GitHub private vulnerability reporting, that must be on in each public, unarchived repository covered (`gh api repos/OWNER/REPO/private-vulnerability-reporting`); it cannot be on in a private, internal or archived one, whose policy names another channel. A service must still take this project's reports. Give the way in: "Report a vulnerability" on the repository's security page, or `https://github.com/OWNER/REPO/security/advisories/new`. Mention private reporting wherever it is on.
- State supported versions as a rule tied to releases ("the latest 2.x minor"); a version table must include the current release and only versions that exist.
- Promise no response time, fix deadline, disclosure window, bounty, safe harbor or CVE process the maintainers have not chosen; a template's numbers are not their choice.
- Say what is not a vulnerability only where the project has a stance (a threat model, trusted inputs, upstream issues).
- Tell reporters to keep reports out of public issues, pull requests, discussions and any chat the project links.
- Keep a what-to-include list short and fit for every channel named; add none where reports go only through GitHub's form.
- When the channel or a program changes, update every line, here or in other docs, that refers to the old one.
- Leave no template text: the "Use this section to tell people..." prompt, `$VMTalias`, example version rows.
